API Reference

Référence complète des endpoints REST et WebSocket du backend PAD.

ℹ️

Base URL

Tous les endpoints sont servis sur http://localhost:8080 par défaut. L'authentification utilise un cookie HttpOnly PAD_Auth.

Authentification

GET /Authentificate Génère un token JWT

Génère un identifiant utilisateur aléatoire, crée un token JWT signé avec la clé Ed25519 privée, et le stocke dans un cookie HttpOnly.

Réponse — Succès 200

{
  "status": "success"
}

En parallèle, le header Set-Cookie est positionné :

Set-Cookie: PAD_Auth=<JWT>; HttpOnly; SameSite=Strict; Path=/

Structure du JWT

// Header
{
  "alg": "EdDSA",
  "typ": "JWT"
}

// Payload
{
  "sub": "4643453044896821454",   // user_id aléatoire
  "exp": 1704150000               // expiration : now + 24h
}

Exemple

curl http://localhost:8080/Authentificate -c cookies.txt -v

Gestion de session

GET /init-sesssion Crée une session de vérification

Requiert le cookie PAD_Auth. Génère un challenge de 4 mouvements aléatoires et une URL S3 pré-signée pour uploader la vidéo de vérification.

⚠️

Limité à 10 appels/heure par utilisateur. Au-delà : 429 Too Many Requests.

Headers requis

  • Cookie string PAD_Auth=<JWT> — token obtenu via /Authentificate

Réponse — Succès 200

{
  "url": "http://localhost:9000/pad-bucket/video_8712.mp4?X-Amz-Algorithm=...",
  "challenge": ["HAUT", "BAS", "GAUCHE", "DROITE"]
}

Champs de réponse

  • url string URL pré-signée S3 (PUT) valide pendant 5 minutes pour uploader la vidéo
  • challenge string[] Séquence de 4 mouvements à réaliser dans l'ordre. Valeurs : HAUT, BAS, GAUCHE, DROITE

Réponses d'erreur

CodeRaison
401Cookie manquant ou JWT invalide/expiré
429Rate limit dépassé (10 req/h)
500Erreur génération URL S3

Exemple

# D'abord obtenir un token
curl http://localhost:8080/Authentificate -c cookies.txt

# Puis initialiser une session
curl http://localhost:8080/init-sesssion -b cookies.txt | jq .

WebSocket — Résultats temps réel

WS /ws/{filename} Canal de résultats asynchrone

Connexion WebSocket utilisée pour signaler la fin de l'upload et recevoir le résultat de l'analyse IA. Le {filename} doit correspondre au nom du fichier vidéo uploadé.

Connexion

// Exemple JavaScript
const ws = new WebSocket('ws://localhost:8080/ws/video_8712.mp4');

Message Client → Serveur

Une fois la vidéo uploadée sur S3, le client envoie :

UploadDone|HAUT,BAS,GAUCHE,DROITE
  • UploadDone prefix Indique que l'upload S3 est terminé
  • challenge string Séquence du challenge reçu (séparateur virgule), dans le même ordre

Message Serveur → Client

// Succès
{
  "status": "IA_SUCCESS",
  "movements": [
    { "frame": 120, "direction": "HAUT", "raw": { "x": 0.02, "y": -0.41 } },
    { "frame": 210, "direction": "BAS",  "raw": { "x": 0.01, "y":  0.38 } }
  ]
}

// Échec (mouvements insuffisants)
{
  "status": "IA_FAIL",
  "movements": [...]
}

// Deepfake détecté
{
  "status": "IA_DEEPFAKE",
  "movements": []
}

// Erreur de traitement
{
  "status": "IA_ERROR",
  "movements": []
}

Codes de statut IA

StatusSignification
IA_SUCCESSChallenge validé — l'utilisateur est considéré présent et vivant
IA_FAILScore insuffisant — les mouvements ne correspondent pas au challenge
IA_DEEPFAKEVidéo identifiée comme deepfake ou rejeu
IA_ERRORErreur technique lors de l'analyse (vidéo corrompue, pas de visage détecté…)

Exemple complet (TypeScript)

async function verifyLiveness() {
  // 1. Auth
  await fetch('/Authentificate', { credentials: 'include' });

  // 2. Session
  const session = await fetch('/init-sesssion', { credentials: 'include' })
    .then(r => r.json());
  // session.url, session.challenge

  // 3. Upload vidéo
  await fetch(session.url, { method: 'PUT', body: videoBlob });

  // 4. WebSocket
  const filename = session.url.split('/').pop().split('?')[0];
  const ws = new WebSocket(`ws://localhost:8080/ws/${filename}`);

  ws.onopen = () => {
    ws.send(`UploadDone|${session.challenge.join(',')}`);
  };

  ws.onmessage = (e) => {
    const result = JSON.parse(e.data);
    console.log(result.status); // "IA_SUCCESS" | "IA_FAIL" | ...
  };
}

Sécurité

Rate Limiting

Le rate limiting est appliqué sur /init-sesssion uniquement. La clé Redis utilisée est ratelimit:{user_id} avec une expiration de 3600 secondes.

JWT — EdDSA (Ed25519)

Les tokens utilisent l'algorithme EdDSA, plus sécurisé et performant que RS256/HS256. Les clés doivent être générées manuellement et montées dans le container backend.

CORS

Allowed-Origin: http://localhost:3000
Allowed-Methods: GET, POST
Allow-Credentials: true
🔴

Production

En production, pensez à : activer HTTPS, mettre Secure sur les cookies, restreindre les origines CORS, et remplacer les credentials MinIO par défaut.
