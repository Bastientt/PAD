Docker & Déploiement

Orchestration Docker Compose, builds multi-stage, variables d'environnement et bonnes pratiques de production.

Services Docker Compose

Le fichier docker-compose.yaml à la racine orchestre l'ensemble de la stack :

ServiceImagePorts exposésDépendances
minio minio/minio:latest 9000, 9001 —
redis redis:alpine 6379 —
backend Build local (Rust) 8080 redis, minio
ia_worker Build local (Python) — redis, minio 
# Lancer toute la stack
docker compose up --build

# En arrière-plan
docker compose up -d --build

# Voir les logs
docker compose logs -f

# Logs d'un service spécifique
docker compose logs -f backend
docker compose logs -f ia_worker

# Arrêter et nettoyer
docker compose down

Dockerfiles

Backend Rust — Build multi-stage

Le backend utilise un build multi-stage pour minimiser la taille de l'image finale (uniquement le binaire compilé dans une image Debian Slim).

# Stage 1 : Compilation Rust
FROM rust:1-slim AS builder
WORKDIR /app
COPY . .
RUN cargo build --release

# Stage 2 : Runtime minimal
FROM debian:bookworm-slim
WORKDIR /app
COPY --from=builder /app/target/release/mon_projet_ws ./
COPY key/ ./key/
EXPOSE 8080
CMD ["./mon_projet_ws"]

AI Worker Python

FROM python:3.11-slim
WORKDIR /app

# Dépendances système pour OpenCV et MediaPipe
RUN apt-get update && apt-get install -y \
    libgl1-mesa-glx libglib2.0-0 ffmpeg && \
    rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY ai_worker.py deepfake_detector.py ./
CMD ["python", "ai_worker.py"]

Configuration des clés JWT

Le backend nécessite une paire de clés EdDSA (Ed25519). Ces clés doivent être générées avant le premier démarrage et ne doivent jamais être versionnées.

# Générer les clés
mkdir -p backend/key
openssl genpkey -algorithm ED25519 -out backend/key/private_key.pem
openssl pkey -in backend/key/private_key.pem -pubout -out backend/key/public_key.pem

# Vérification
cat backend/key/public_key.pem
🔴

Ne jamais committer les clés

Le dossier backend/key/ est (et doit rester) dans le .gitignore. En production, injecter les clés via des secrets Docker ou des variables d'environnement.

MinIO — Configuration initiale

Au premier démarrage, MinIO ne contient aucun bucket. Il faut créer pad-bucket manuellement ou via la CLI :

# Via la CLI mc (MinIO Client)
docker run --rm -it \
  --network pad_default \
  minio/mc \
  alias set local http://minio:9000 minioadmin minioadmin

docker run --rm -it \
  --network pad_default \
  minio/mc \
  mb local/pad-bucket

# Rendre le bucket accessible
docker run --rm -it \
  --network pad_default \
  minio/mc \
  anonymous set download local/pad-bucket

Déploiement en production

Checklist sécurité

  • Remplacer les credentials MinIO par défaut (minioadmin/minioadmin)
  • Activer HTTPS sur le backend (reverse proxy Nginx/Traefik)
  • Mettre le flag Secure sur le cookie JWT
  • Restreindre les origines CORS à votre domaine
  • Configurer Redis avec un mot de passe (requirepass)
  • Ajouter des limites de ressources (mem_limit) dans Compose
  • Configurer des health checks sur chaque service
  • Persister les données Redis avec un volume si nécessaire

Exemple avec Nginx reverse proxy

server {
    listen 443 ssl;
    server_name pad.votre-domaine.com;

    ssl_certificate     /etc/ssl/certs/pad.crt;
    ssl_certificate_key /etc/ssl/private/pad.key;

    location / {
        proxy_pass         http://localhost:8080;
        proxy_http_version 1.1;
        proxy_set_header   Upgrade $http_upgrade;
        proxy_set_header   Connection "upgrade";    # WebSocket
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
    }
}

Health checks

# Vérifier que le backend répond
curl http://localhost:8080/Authentificate

# Vérifier Redis
redis-cli ping   # → PONG

# Vérifier MinIO
curl http://localhost:9000/minio/health/live   # → 200 OK
